Cove Agent MCP connects an AI agent to your Cove trading profile through the [Model Context Protocol](https://modelcontextprotocol.io/). The agent can inspect balances and positions, research tokens, execute trades, manage automated orders, and—with an additional permission—move funds.

<Warning>
  **Access is invite-only and disabled by default.** Cove must grant MCP access to the wallets you want to connect before you can mint agent tokens. After that grant, you control each wallet's trade and money-out capabilities from `/agent` in Telegram.
</Warning>

## At a glance

| | |
|---|---|
| **Endpoint** | `POST https://cove.trade/api/mcp` |
| **Authorization** | `Authorization: Bearer <your-token>` |
| **Protocol** | Model Context Protocol over Streamable HTTP (JSON-RPC 2.0) |
| **Default rate limit** | 30 requests per minute across all of your agent tokens |
| **Access scope** | A newly minted token pair is pinned to one profile |
| **Wallet scope** | One or more selected wallets from that profile |
| **Trading mode** | Real and paper wallets require separate token pairs |

An MCP client discovers the tools available to its token automatically after connecting.

## How profile and wallet scope works

When you mint a token pair, you select one or more wallets. Cove derives their profile and pins the new token to it. You do not need a separate token for every wallet, but a token cannot span profiles.

<Columns cols={2}>
  <Card title="One profile per token" icon="layer-group">
    Select wallets from one profile. Mint a separate token pair for each additional profile.
  </Card>

  <Card title="Selected wallet scope" icon="wallet">
    A token reaches only the wallet IDs selected during minting, not every wallet added to the profile later.
  </Card>

  <Card title="Per-wallet capabilities" icon="shield-check">
    Every wallet in scope reports its own `read`, `trade`, or `money_out` capability.
  </Card>

  <Card title="Profile limits" icon="folder-tree">
    A user can have up to 5 non-paper profiles with 10 wallets each and up to 10 archived profiles. The paper profile sits outside the 5-profile cap.
  </Card>
</Columns>

Manage profiles with `/profiles` in Cove and wallet access with `/agent` in Telegram.

<Note>
  Tokens minted before profile pinning remain scoped to the wallets they were originally issued over. Re-mint the pair to pin it to a profile. `get_profile` reports legacy scope instead of inventing a profile.
</Note>

## Quick start

<Steps>
  <Step title="Request profile access">
    [Open a support ticket](/features/support) and list the profile and wallets you want enabled for MCP. This is the admin grant that allows those wallets to participate in agent access.
  </Step>

  <Step title="Choose wallets and mint tokens">
    After Cove enables the wallets, open `/agent` in Telegram, choose the wallet scope, and mint a **read** / **read-write** pair. For programmatic setup, call `POST /agent/tokens` with `accountIds`; see [Mint and manage tokens](#mint-and-manage-tokens).

    Your Cove account must be linked to Telegram before you can mint tokens. Cove sends trade notifications there.
  </Step>

  <Step title="Configure your MCP client">
    Point the client at the MCP endpoint and send the selected token as a Bearer token.

    ```json
    {
      "mcpServers": {
        "cove": {
          "url": "https://cove.trade/api/mcp",
          "headers": {
            "Authorization": "Bearer <your-agent-token>"
          }
        }
      }
    }
    ```

    <Note>
      MCP client configuration formats vary. Use the equivalent URL and headers fields if your client does not use an `mcpServers` object.
    </Note>
  </Step>

  <Step title="Verify read access">
    Start with `get_profile` and `list_accounts` to discover the connected profile, available wallet IDs, and wallet capabilities. Then try `get_positions` and `search_tokens` with the read token.
  </Step>

  <Step title="Enable trading only when needed">
    Give the agent the read-write token only if it must trade or change settings. Pass the intended wallet IDs in `accountIds`, and use a unique `idempotencyKey` for every intended operation.
  </Step>
</Steps>

## Enable access

Agent access has two layers:

<Columns cols={2}>
  <Card title="1. Cove access grant" icon="user-shield">
    [Ask support](/features/support) to enable MCP for the intended profile and wallets. Without this grant, the wallets cannot be included in an agent token.
  </Card>

  <Card title="2. Your wallet capabilities" icon="sliders">
    Use `/agent` to choose the wallet scope and turn trading or money-out on or off for each wallet independently.
  </Card>
</Columns>

<Warning>
  REST token minting starts selected wallets with trading enabled and money-out disabled. To allow withdrawals or transfers, the user must enable money-out for each wallet in `/agent`; a support ticket does not turn on that user capability.
</Warning>

## Tokens and permissions

Minting creates a read/read-write pair for the selected wallet scope. Cove pins a newly minted pair to the profile that owns those wallets.

<Columns cols={2}>
  <Card title="Read token" icon="eye">
    Use for monitoring, reporting, token research, earnings, and exports. It cannot trade, change settings, request payouts, withdraw, or transfer funds.
  </Card>

  <Card title="Read-write token" icon="pen">
    Includes all read access, plus trading, automated orders, settings changes, and payout requests. Withdrawals and transfers work only when money-out is also enabled.
  </Card>
</Columns>

### Permission matrix

| Capability | Read | Read-write | Extra permission |
|---|:---:|:---:|---|
| Balances, positions, orders, and history | ✓ | ✓ | — |
| Token search and security research | ✓ | ✓ | — |
| Market trades and automated orders | — | ✓ | — |
| Read settings, earnings, and exports | ✓ | ✓ | — |
| Change settings or request a payout | — | ✓ | — |
| Withdraw or transfer funds | — | ✓ | Money-out |

Write tools return a permission error when called with a read token.

<Note>
  Token permission and wallet capability are separate checks. A read-write token can trade only the wallets whose capability permits trading. Call `list_accounts` instead of assuming every wallet has the same access.
</Note>

### Mint and manage tokens

Use `/agent` in Telegram for normal setup and lifecycle management. Use the REST API when your application needs to automate token creation or revocation. These are management surfaces, not MCP tools.

<Tabs sync={false}>
  <Tab title="Telegram /agent" icon="message-circle">
    The `/agent` panel lets the user:

    - Choose the wallets included in the token scope.
    - Toggle trading and money-out for each wallet.
    - Set or clear per-trade, hourly, daily, and per-batch spending limits.
    - Configure an agent webhook.
    - Mint or rotate the read/read-write token pair.
    - Revoke all agent tokens.

    Use this panel whenever the user must change a wallet capability. REST minting cannot enable money-out.
  </Tab>

  <Tab title="REST API" icon="code">
    | Endpoint | Purpose |
    |---|---|
    | `POST /agent/tokens` | Mint or replace a read/read-write pair for the selected wallets. Returns `isPaper`. |
    | `GET /agent/tokens` | List active tokens, including `isPaper`. |
    | `DELETE /agent/tokens/:id` | Revoke one token. |
    | `DELETE /agent/tokens/all` | Revoke all agent tokens. |

    Authenticate these endpoints with the user's normal Cove/Privy session. The Cove account must be linked to Telegram.

    Request body:

    ```jsonc
    {
      "accountIds": ["<walletId>", "<walletId>"],
      "label": "my-agent"
    }
    ```

    | Field | Required | Rules |
    |---|---|---|
    | `accountIds` | Yes, unless using `accountId` | Array of 1–25 wallet IDs. All wallets must belong to one profile and all must be either real or paper. |
    | `accountId` | Deprecated alternative | Single-wallet alias. Send exactly one of `accountIds` or `accountId`. |
    | `label` | No | Human-readable label, up to 64 characters. |

    The request schema is strict: unknown keys are rejected. In particular, `chatId` is no longer accepted because notifications go to the linked Telegram account.
  </Tab>
</Tabs>

<Info>
  Token-management endpoints have their own 30-requests-per-minute limit. It is separate from the MCP tool-call limit and cannot be increased by an admin override.
</Info>

### Paper trading tokens

An agent token is either **all real** or **all paper**. Do not mix real and paper wallet IDs in one mint request; create a separate pair for each mode.

- `POST /agent/tokens` and `GET /agent/tokens` return `isPaper`.
- Paper accounts never expose wallet addresses through `list_accounts`.
- `export_trades` always excludes paper trades.
- The paper profile is a first-class profile and does not count toward the five non-paper profile limit.

### Webhooks

Configure an optional agent webhook from `/agent`. Webhooks cover market and transfer orders. Cove encrypts webhook credentials at rest, and rotating a token pair carries the webhook configuration forward.

<Warning>
  Treat read-write tokens as secrets. If a token may have been exposed, rotate the pair immediately from `/agent`. Rotation does not reset rate limits or spending caps; those limits follow your account rather than an individual token.
</Warning>

## Work across wallets

A single agent token can reach one or many wallets in its profile. Call `list_accounts` to discover the wallet IDs the token can use, their capabilities, and—when requested—their individual USDC balances.

<Info>
  Cove profiles currently contain up to 10 wallets. Parameters that accept an `accountIds` array allow 1–25 IDs, so clients should follow the tool schema rather than hard-code the current profile size.
</Info>

### Choose wallets explicitly

| Parameter | Shape | Use it for |
|---|---|---|
| `accountId` | One wallet ID | Limit orders, DCA, money-out, `sync_positions`, `get_deposit_addresses`, and `get_balance`. It also works as a single-wallet alias on supported reads. |
| `accountIds` | Array of 1–25 wallet IDs | Required by `buy_token`, `sell_token`, and `batch_order`. Optional on `get_positions`, `get_trading_history`, and `export_trades`. |
| Omit both | No wallet filter | Read from every in-scope wallet on supported fan-in tools. `get_balance` may omit `accountId` only when the token reaches exactly one wallet. |

<Warning>
  Do not send `accountId` and `accountIds` together. Cove refuses the request instead of guessing which wallet selection you intended.
</Warning>

### Wallet behavior by operation

<Tabs sync={false}>
  <Tab title="Read across wallets" icon="eye">
    `get_positions`, `get_trading_history`, and `export_trades` default to every wallet in scope when you omit a target. Each returned row identifies its source wallet.

    Narrow these reads with `accountIds`, or use `accountId` for one wallet. `get_balance` is always a per-wallet result and normally requires `accountId`.
  </Tab>

  <Tab title="Trade across wallets" icon="arrow-right-arrow-left">
    `buy_token`, `sell_token`, and `batch_order` require `accountIds` and fan out across the selected wallets. Every wallet trades independently and receives its own order.

    The response contains one outcome per wallet:

    - `submitted` — includes that wallet's order ID.
    - `refused` — includes an actionable reason, such as an amount below the minimum.
    - `failed` — reports the unsuccessful wallet operation.

    A partial fan-out is never reported as a clean success. When selling by `amountUsd`, Cove calculates a different percentage of each wallet's own position. Every fill sends its own Telegram notification.
  </Tab>

  <Tab title="One wallet per call" icon="wallet">
    Limit orders, DCA ladders, and all money-out tools intentionally act on one wallet through `accountId`. Create or run them separately for each wallet.

    Tools that update or cancel a specific existing order can target the order or group directly by its ID, as shown in the tool reference.
  </Tab>
</Tabs>

## Rate limits

The default limit is **30 requests per minute**, counted across all of your agent tokens together.

To request more capacity, [open a support ticket](/features/support) with:

- The type of agent and its workload.
- Your expected calls per minute.
- Whether traffic is steady, bursty, or scheduled.
- Your requested requests-per-minute limit.

Cove reviews higher limits based on the use case.

## Safety and execution rules

### Use idempotency keys for every write

Every trade, withdrawal, and transfer requires an `idempotencyKey`. Generate one unique value for each intended operation and persist it before sending the request.

If a request times out, retry with the **same key**. Cove returns the original result instead of creating a second operation. Use a new key only for a genuinely new action.

```text
Intent: Buy $100 of a token
First attempt:  idempotencyKey = "5db42d9e-6b8c-44cb-8c2f-cb0fb28d21ab"
Retry:         idempotencyKey = "5db42d9e-6b8c-44cb-8c2f-cb0fb28d21ab"
Next buy:      idempotencyKey = <new unique value>
```

### Handle high price impact explicitly

A trade with unusually high price impact pauses and asks for confirmation. Re-submit the same operation with `confirmHighImpact: true` only after applying your agent's approval policy.

<Warning>
  A confirmation response that mentions a **ceiling** is a hard Cove safety floor. No user setting can disable it. Escalate the decision to the user; do not auto-confirm it.
</Warning>

<Danger>
  Treat a read-write token as capable of irreversible loss even when money-out is disabled. A high-slippage swap against an attacker-controlled pool can consume the full input, and a read-write token may update slippage settings. Prompt injection through attacker-authored token metadata is a realistic trigger. Use strict spending caps, isolate untrusted content, and require human approval for high-risk changes.
</Danger>

### Additional protections

- **Sellability check:** Cove refuses a buy that would leave a position below the sell floor: **$2.50 on Solana** and **$0.50 on other chains**.
- **Optional spending caps:** Use `/agent` to set maximum spend per trade, per hour, per day, and per batch. The batch cap bounds the total fan-out.
- **Fail closed:** If Cove cannot verify the agent's open exposure, it refuses new trades instead of risking an overspend.
- **Read isolation:** A read token cannot spend or move funds.
- **Telegram notifications:** Every trade fill sends a message to the Telegram account linked to Cove.

## Tool reference

The tables below show both the minimum token access and how each tool targets wallets.

- **All** — defaults to every in-scope wallet; narrow with `accountIds` or the `accountId` alias.
- **Fan-out** — requires `accountIds`; creates one independent order per wallet.
- **One** — requires a single `accountId` unless otherwise noted.
- **Profile**, **User**, or **By ID** — does not select wallets directly.

### Account and portfolio

| Tool | Access | Wallet targeting | Description |
|---|---|---|---|
| `get_balance` | Read | One | Return one wallet's spendable USDC and the state of funds bridging or waiting to bridge. `accountId` may be omitted only when the token reaches one wallet. |
| `get_positions` | Read | All | Return open positions with live PnL and cost basis. Every row identifies its wallet. |
| `get_trading_history` | Read | All | Return recent orders with amounts, fees, status, transaction hashes, and wallet IDs. Supports exact status filtering. |
| `sync_positions` | Read | One | Refresh one wallet's positions from on-chain data, like **Refresh** in `/positions`. |
| `get_order_status` | Read | By order ID | Return the status of one order. |
| `list_accounts` | Read | Profile | List the wallets this token can use, their IDs and capabilities, and optional per-wallet USDC balances. |
| `get_deposit_addresses` | Read | One | Return one wallet's deposit addresses by chain. On ERC-4337 chains, this is the smart-account address. |
| `get_profile` | Read | Profile | Return the profile connected to the agent token. |

<AccordionGroup>
  <Accordion title="get_balance bridging fields" icon="arrow-right-arrow-left">
    `get_balance` separates non-primary-chain funds by what happens next:

    | Field | Meaning | Client behavior |
    |---|---|---|
    | `consolidatingUsd` | Funds are bridging now. | Safe to poll. |
    | `parkedUsd` | Funds are waiting for the user's `/bridge` approval. | Do not poll as if arrival were automatic. |
    | `stuckUsd` | Funds are below the bridge floor. | Ask the user to top up. |
    | `autoBridgeMode` | `auto`, `manual`, or `unknown`. | Use it to explain why funds are moving or parked. |
  </Accordion>

  <Accordion title="list_accounts byChain totals" icon="coins">
    `byChain` contains one row per **chain and stable token**, not one row per chain. A chain may have separate USDC and USDT/alias rows.

    Do not select a chain with only `.find(chainName)`. Match `tokenSymbol`, or sum every row for the intended `chainId`. Use `spendableUsd` and `totalUsd` as the authoritative wallet totals.
  </Accordion>

  <Accordion title="get_trading_history status values" icon="clock-rotate-left">
    The `status` filter accepts:

    ```text
    pending | claiming | executing | triggered | success | failed | cancelled | expired
    ```

    Use `success`, not `filled`. When automatic TP/SL is enabled, unfilled protective rungs can appear as `cancelled` rows with zero amounts after the position is fully sold. These are orders that never executed, not lost trades.
  </Accordion>
</AccordionGroup>

### Token research

| Tool | Access | Wallet targeting | Description |
|---|---|---|---|
| `search_tokens` | Read | — | Find tokens by name or symbol. |
| `get_token_info` | Read | — | Return detailed token information by address. |
| `get_token_security_report` | Read | — | Return the Cove security signal: audit verdict, mint and freeze authority, top-10 holder concentration, holder count, liquidity locks, and launchpad information. |

### Market trades

| Tool | Access | Wallet targeting | Description |
|---|---|---|---|
| `buy_token` | Read-write | Fan-out, 1–25 | Market-buy independently across `accountIds`. Requires `tokenAddress`, `chainId`, `amountUsd`, and `idempotencyKey`. |
| `sell_token` | Read-write | Fan-out, 1–25 | Market-sell each wallet's position by `percent` from 1–100 or by `amountUsd`. Also requires `idempotencyKey`. |
| `batch_order` | Read-write | Fan-out, 1–25 | Open a new position for each eligible wallet and attach a stop-loss, take-profit, or both. Refuses wallets that already hold the token. |

<Accordion title="batch_order execution details" icon="layer-group" defaultOpen>
  - For an existing position, use `buy_token` and then `create_stop_loss` / `create_take_profit` instead.
  - TP/SL triggers are anchored to the market price when the buy is **accepted**, not the later realized fill price, because execution is asynchronous.
  - If a wallet's buy ultimately fails, its protective orders find no balance and are cancelled automatically.
</Accordion>

### Automated and limit orders

| Tool | Access | Wallet targeting | Description |
|---|---|---|---|
| `create_limit_buy` | Read-write | One | Buy for one `accountId` when price moves by a percentage or reaches a target market cap. Supports dip buys and breakouts. |
| `create_stop_loss` | Read-write | One | Sell one wallet's existing position after price falls by the configured percentage. |
| `create_take_profit` | Read-write | One | Sell one wallet's existing position after price rises by the configured percentage. |
| `create_trailing_stop` | Read-write | One | Track one wallet's peak price and sell when price drops by the configured percentage from that peak. |
| `create_dca_ladder` | Read-write | One | Spread multiple buy or sell orders for one wallet across a market-cap range. Returns a `groupId`. |
| `update_limit_order` | Read-write | By order ID | Edit a pending order's trigger, size, or expiry. |
| `get_limit_orders` | Read | One | List active limit orders for one `accountId`. |
| `cancel_limit_order` | Read-write | By order ID | Cancel one order. |
| `cancel_limit_orders` | Read-write | One | Cancel all active orders, or all active orders for one token, in one wallet. |
| `cancel_dca_group` | Read-write | One | Cancel a whole DCA ladder by `groupId` for one wallet. |

### Settings, earnings, and exports

| Tool | Access | Wallet targeting | Description |
|---|---|---|---|
| `get_settings` | Read | Profile | Return profile-wide trade and position settings. Execution settings include `stored` and `effective` values. **Always size trades from `effective`** because degen mode can override slippage and protections at read time. |
| `update_settings` | Read-write | Profile | Update supplied profile-wide fields. Slippage, max-buy clamp, and liquidity protection each disable degen mode in the same write. |
| `get_earnings` | Read | User | Return cashback and affiliate earnings, including pending balance, lifetime paid, rate or tier, and payout eligibility. |
| `request_payout` | Read-write | User | Request a payout of pending earnings to the primary wallet. The request is audited and consumes the 24-hour cooldown. |
| `export_trades` | Read | All | Export trade history as `koinly` CSV for tax import or `generic` CSV for spreadsheets. Every row identifies its wallet. |

<Warning>
  In one `update_settings` call, send at most one of `slippageBps`, `clampToMaxBuy`, or `liquidityProtectionEnabled`. Never send any of those fields together with `degenMode: true`.
</Warning>

### Withdrawals and transfers

These tools require a read-write token and money-out enabled for the source wallet. All operations are irreversible, act on one `accountId`, and require an `idempotencyKey`.

| Tool | Access | Wallet targeting | Description |
|---|---|---|---|
| `withdraw_usdc` | Read-write + money-out | One | Withdraw a fixed USDC `amount` from one wallet to an external wallet, or use `max` to withdraw the full available amount. |
| `withdraw_token` | Read-write + money-out | One | Send a non-stablecoin position token from one wallet to an external address on the same chain. Supports native SOL, ETH, and HYPE. |
| `transfer_usdc` | Read-write + money-out | One | Send Solana USDC from one wallet to another Cove user by Telegram username. |
| `transfer_token` | Read-write + money-out | One | Move 1–100% of the source wallet's token balance, including USDC, to another in-scope wallet on the same chain. Transfers never cross the profile boundary. |

<Note>
  Cross-chain `withdraw_usdc` has a **$0.25 flat fee**. Same-chain Solana withdrawals have no flat fee; on-chain rent applies only when the recipient does not already have a USDC token account. `withdraw_token` rejects stablecoins—use `withdraw_usdc` for external stablecoin withdrawals.
</Note>

## Errors and availability

Tool failures include a readable message and a machine-readable `code`, such as:

| Code | Meaning |
|---|---|
| `below_min` | The requested operation is below an allowed minimum. |
| `no_position` | The connected profile does not have the required position. |
| `price_unavailable` | Cove cannot currently determine a usable token price. |
| `invalid_input` | One or more request fields are invalid. |
| `confirmation_mismatch` | A high-impact confirmation does not match the original operation. |
| `confirmation_expired` | The high-impact confirmation window has expired. |
| `token_not_found` | Cove cannot resolve the requested token. |
| `insufficient_balance` | The selected wallet does not have enough spendable balance. |
| `position_exists` | The operation requires a new position, but the wallet already holds the token. |

### Token mint refusals

REST token management uses regular HTTP responses:

| HTTP status | Response detail | What to do |
|---:|---|---|
| `400` | Invalid body, both wallet selectors, mixed paper/real wallets, or another scope violation | Correct the request. Use exactly one selector and one trading mode. |
| `403` | `ungrantedAccountIds` | Ask Cove support to enable MCP for those wallets. |
| `409` | `signerLostAccountIds` | The user must restore signing access for those wallets in Cove. |

<Warning>
  If a withdrawal result is uncertain—for example, the connection drops after signing—an idempotent retry returns an error rather than reporting success. Check `get_order_status` before assuming the withdrawal completed or submitting another one.
</Warning>

Cove may pause MCP globally for maintenance or an emergency. The endpoint returns **HTTP 503** with JSON-RPC error code `-32000` and one of these messages:

```text
MCP endpoint is temporarily paused
MCP endpoint is disabled
```

Clients should stop writes and retry only after service resumes.
